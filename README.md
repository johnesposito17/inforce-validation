# In-Force Data Validation Tool

An Excel/VBA utility that validates a life insurance **in-force extract** before it
feeds an actuarial valuation, applying six data-quality checks and producing a
severity-ranked exception report and summary dashboard.

---

## Why I built this

Every reporting period, a life insurer runs a **valuation** — the calculation of
policy reserves and liabilities across its entire book of in-force business. That
calculation is only as trustworthy as the data going into it. A single duplicated
policy double-counts a reserve; a negative or zero face amount produces a nonsensical
liability; a policy dated *after* the valuation date shouldn't be in the extract at
all; a missing sex code or an unrecognized product code means no mortality rate or
valuation basis can be assigned. Errors like these are cheap to fix **before** the
run and expensive to chase down **after** the numbers are already wrong. This tool
does the up-front scrub: it scans the extract, flags every record that would break or
distort the valuation, and ranks the findings so the reviewer fixes the dangerous
ones first.

## What it does

Point the tool at an `InForce` worksheet and it scans every policy row, applies six
data-quality checks, and writes two outputs:

- **`Exceptions`** — a severity-ranked, colour-coded report. One row per problem
  found, with the policy number, source row, which check failed, the offending value,
  and a plain-English explanation of *why it matters for the valuation*. Sorted
  High-first and filterable.
- **`Summary`** — a one-glance dashboard: total exceptions, a breakdown by severity,
  and a breakdown by individual check (every check is listed, so a check that found
  nothing shows a **0** — proof it ran rather than silence). A **Run Validation**
  button on this sheet kicks off the scan.

## The six checks & severity scheme

Each finding is tagged **High** or **Medium**:

- **High = stop and fix** — the record would corrupt the valuation (double-counted
  reserves, negative liabilities, un-valuable policies). Don't run until resolved.
- **Medium = flag and proceed with caution** — the record is suspect and a rate may
  not apply cleanly, but it won't break the run outright.

| # | Check | What it catches | Severity |
|---|-------|-----------------|----------|
| 1 | **Policy number** | Blank policy number, or a duplicate of one already seen | High |
| 2 | **Issue age** | Missing/non-numeric, or outside the plausible **18–85** issue band | Medium |
| 3 | **Face amount** | Missing/non-numeric, or **zero / negative** | High |
| 4 | **Issue date** | Missing/unreadable, or **after the valuation date (2024-12-31)** | High |
| 5 | **Sex code** | Blank, or not one of `M` / `F` | Medium |
| 6 | **Product code** | Blank, or not on the approved list (`TRM10, TRM20, TRM30, WL, UL`) | High |

## How I tested it

The checks are only worth trusting if you can prove they catch what they claim to.
The repo includes an **error injector** (`Module1`) that does exactly that:

1. Start from clean synthetic policy data on the `InForce` sheet.
2. Run **`InjectErrors`**. It deliberately corrupts ~3% of rows — one of the six
   error types per row (duplicating a policy number, zeroing an age, negating a face
   amount, post-dating an issue date, blanking a required field, or swapping in an
   unapproved product code).
3. Every corruption is logged to an **`AnswerKey`** sheet: the row, the field broken,
   and exactly what was done — a machine-generated **ground truth**.
4. Run the validator and reconcile the `Exceptions` report against the `AnswerKey`.
   Every injected error should surface as an exception at the right row and severity.

Because the answer key is generated by the same run that injects the errors, the test
is self-verifying: there's no hand-maintained expected-output file to drift out of date.

![Answer key logging every deliberately injected error — the ground truth used to verify the validator actually catches what it should.](screenshots/answerkey.png)

## Input format

The tool reads a sheet named **`InForce`** with a header row and one policy per row:

| Col | Field | Notes |
|-----|-------|-------|
| A | Policy Number | must be present and unique |
| B | Product Code | must be on the approved list |
| C | Sex | `M` or `F` |
| D | Issue Age | 18–85 |
| E | Issue Date | on or before the valuation date |
| F | Face Amount | positive |
| G | Annual Premium | carried through; not validated |

Sample data lives in [`sample-data/`](sample-data/) as CSV so reviewers can inspect it
without opening Excel.

## How to run it

1. Open **`InForce_Validation.xlsm`** and **enable macros** when prompted.
2. *(Optional — to reproduce the test)* Run **`InjectErrors`** (`Module1`) to corrupt
   ~3% of the sample rows and build the `AnswerKey` sheet.
3. Run the validation — either:
   - click the **Run Validation** button on the `Summary` sheet, or
   - press <kbd>Alt</kbd>+<kbd>F8</kbd>, choose **`RunDataChecks`**, and Run.
4. Review the **`Exceptions`** report (worst-first) and the **`Summary`** dashboard.

Configuration (valuation date, age band, approved product list, sheet names) lives in
labelled constants at the top of `Module2` — no need to touch the check logic to
re-point it at a different book.
